# Project Context

## Active product

The active product is an image-only, local-first FLUX creation workspace. The active task API is `/api/local-lab/image-tasks`, and the local LoRA registry API is `/api/local-lab/image-loras`; tasks and registry state are stored in ignored project-local state under `.secrets/image-studio/`.

## Image task contract

- Stack: Fluxed Up 10.2 BF16 as the complete FLUX transformer replacement, shared FLUX encoders/VAE, the pinned AIDMA NSFW Unlock LoRA, and an ordered set of optional registered LoRAs.
- A positive prompt is required. A separate optional negative prompt is persisted and sent to its own `CLIPTextEncode` node. Reference-image tasks are intentionally deferred and blocked as `FLUX Kontext 执行器尚未完成`.
- Supported text controls: steps 25-40, legacy single-LoRA strength 0.6-1.1, each registered LoRA strength 0.0-1.5, CFG 3.5-5.0, Euler or FlowMatch, and 768-1536 px dimensions in 256 px increments.
- “添加新的LoRA” performs a zero-network, server-side URL recognition step and persists a `registered` source before any provider metadata or model bytes are requested. It accepts Civitai `.com`/`.red` model pages and version/fileId downloads, HuggingFace/`hf.co` repositories and file URLs, plus recognizable HTTPS download/`.safetensors` links. The raw registration URL remains only in the ignored server-side registry and is never returned by the API.
- Creating a `pending_confirmation` card is network-free: the server validates only registry-owned LoRA IDs plus strength/enabled values and persists them as `loraSelections`. Confirmation resolves each enabled `registered` Civitai or HuggingFace source once to a concrete FLUX.1-compatible filename, immutable provider revision/file, advertised size, and SHA-256, then atomically attaches the canonical `loras` snapshot before moving the card to `waiting_for_gpu`. A failed resolution leaves the card unchanged and cannot reach rental. The existing pre-order delivery refresh and Agent full-byte size/SHA/safetensors checks remain unchanged. A generic direct URL without a trustworthy expected identity may be registered for later editing, but confirmation fails locally and clearly before an order can be created.
- Tasks at or below 1280 x 1280 use RTX 4090 (`低`); all larger dimensions use RTX 5090 (`高`).
- Text-generation dimensions are limited to 768-1536 in 256-pixel increments. Both dimensions at or below 1280 require RTX 4090; either dimension above 1280 through 1536 requires RTX 5090; larger or non-grid dimensions are rejected with a clear local error.
- RTX 5090-class tasks enter the same local pending-confirmation queue as RTX 4090 tasks. A confirmed batch is frozen to exactly one GPU class; the shared executor chooses the cheapest compliant online on-demand host of that exact class, verifies the post-start GPU report, and preserves the existing one-order, reserve-balance, cost, watchdog, and cleanup guards.
- RTX 4090 text batches (768-1280, 256-pixel grid, no reference image) use only deployment profile `rtx4090-golden-agent-v1`: `cloreai/jupyter:ubuntu24.04-v2`, HTTP `8080`, Agent `/healthz`, and the immutable Agent/Controller/Workflow identities recorded in `IMAGE_E2E_GOLDEN_BASELINE.json`. The historical custom GHCR runtime digest is experimental and unready for the normal UI path after identical proxy-502 failures on two hosts. RTX 5090 requires its own newly published and pinned immutable digest containing the 1536-capable workflow; until then it fails closed with a class-specific unpublished-runtime blocker rather than renting the 4090 image.
