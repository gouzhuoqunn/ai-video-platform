# Project Context

## Active product

The active product is an image-only, local-first FLUX creation workspace. The only active task API is `/api/local-lab/image-tasks`; tasks are stored in ignored project-local state under `.secrets/image-studio/tasks.json`.

## Image task contract

- Stack: Fluxed Up 10.2 BF16 as the complete FLUX transformer replacement, shared FLUX encoders/VAE, and AIDMA NSFW Unlock LoRA.
- Prompt is required. Reference-image tasks are intentionally deferred and blocked as `FLUX Kontext 执行器尚未完成`.
- Supported text controls: steps 25-40, LoRA 0.6-1.1, CFG 3.5-5.0, Euler or FlowMatch, and 768-2048 px dimensions in 256 px increments.
- Tasks at or below 1280 x 1280 use RTX 4090 (`低`); all larger dimensions use RTX 5090 (`高`).

## RTX 4090 executor checkpoint

- The Studio left GPU panel persists maximum hourly price, runner session state, host details, stage, timestamps, and copyable backend errors.
- The paid rental button remains disabled by default until the image executor readiness gate is explicitly satisfied.
- The HTTP-first RTX 4090 runner has a no-order dry mode, freezes selected task IDs and maximum hourly price, uses `COMFY_NODE_PROFILE=image-flux`, and never waits for SSH.
- RTX 4090 readiness now requires `IMAGE_4090_EXECUTOR_READY=true` plus either a strict local validated restore manifest or a complete first-run bootstrap configuration. Runner preflight failures are persisted to the Studio session instead of leaving stale searching progress.
- Image batch cancellation is exposed through the local image task API and cancels the matching current image Clore order directly from persisted session/order state; it is idempotent when the order is already gone and does not depend on the runner PID.
- Image create-order now uses a bounded single request and advances persisted state as soon as an order ID is known. HTTP readiness is a separate 12-minute path with deployment, endpoint, `/healthz`, elapsed-time, and cancellation diagnostics; after timeout or runner exit the API reconciles live Clore orders before deciding whether to fail, clear stale local state, or surface an active billing risk.
- Runtime `/healthz` now proves the HTTP controller is alive independently from ComfyUI; the image runner waits for `ready: true`, while `ready: false`/`runtime_failed` keeps diagnostics visible instead of becoming a proxy-level 502.
- The restricted Clore diagnostic Agent is bootstrapped from an immutable public source commit. Its controller stage fetches only the pinned Controller and workflow files by immutable raw URL and verified SHA-256; it never clones the project repository.
- Runtime bootstrap binds the HTTP controller before touching `/workspace`; initial controller state and logs live under `/tmp/image-runtime-bootstrap`, and unwritable `/workspace` failures surface as `workspace_failed` health JSON while the container stays alive.
- Before an order ID exists, the image runner may only show `creating_order` or `create_order_failed`; HTTP endpoint waiting is shown only after a real order ID exists. Transient create-order network errors persist sanitized nested fetch cause details, reconcile `/my_orders`, then retry exactly once only if no order was created.
- A local active-order JSON file or create lock is never trusted by itself. Studio refresh/start/cancel and the low-level create-order guard reconcile Clore `/my_orders`; if the provider has zero active orders, stale local order/lock/session execution state is cleared while preserving confirmed image tasks.
- After an order ID is known or reconciled, every post-order failure path attempts cancellation and verifies active Clore orders return to zero.
- If a Clore image order has an HTTP public hostname but remains `deploying` with only proxy-level `/healthz` 502 responses for 6 minutes, the runner cancels the order, preserves the image task, records a deployment failure, and temporarily denies that host for 24 hours.
- Source acquisition manifests are separate from validated R2 restore manifests. Source manifests may omit unavailable hashes; restore manifests require exact size, SHA-256, runtime destination, cache key, and presigned download URL.
- Successful PNG results are validated for signature and exact dimensions, hashed, thumbnailed, and persisted under `AI_IMAGE_LIBRARY_ROOT` (default `D:\AI-Video-Library\images`), outside the repository.
- The restricted Clore diagnostic Agent now has authenticated, fixed stages for raw immutable controller/workflow retrieval, CUDA ComfyUI bootstrap, exactly five verified model files, one fixed FLUX inference request, and authenticated PNG artifact retrieval. The fixed FLUX graph uses `EmptySD3LatentImage` with the requested width and height directly; it gates that node through ComfyUI `object_info` before submitting a prompt. It never accepts shell commands, workflow JSON, arbitrary paths, permanent cloud credentials, or model destinations from the remote caller.
- The ComfyUI stage reuses a healthy existing virtual environment. If the official Ubuntu image specifically lacks `ensurepip` / the Python venv package, it may run only fixed bounded `apt-get update` and noninteractive `python3.12-venv` installation commands before recreating and probing that same virtual environment; it never accepts a package name or shell input from the caller.
- The fixed CUDA runtime stack is Torch 2.8.0, torchvision 0.23.0, and torchaudio 2.8.0 from the CUDA 12.8 PyTorch index. The Agent filters only those three direct requirements from the pinned ComfyUI requirements file, installs the remainder under fixed constraints, and retains complete local pip logs with bounded sanitized error/final-line summaries in Agent status and logs responses.
- The local JSON task list is the source of truth. `src/lib/image-generation/local-image-task-store.ts` serializes all reads and mutations with a cross-process lock directory, stale-lock recovery, fsync-plus-atomic JSON replacement, short local leases, hashed claim tokens, and exact-task-only finalization.
- The Image Studio prompt workspace supports a positive safe-integer continuous-generation count. `create_group` atomically appends independently seeded child tasks sharing explicit group metadata; `regenerate_group` appends children to the same explicit or synthetic legacy group without rewriting completed artifacts. The Results tab groups completed children, while the prompt tab’s right rail shows compact active groups. Cards can be multi-selected without extinguishing earlier selections, use the prompt as a width-clamped title, and provide local-only per-card confirmation/deletion plus a header batch-confirmation action. The left GPU panel contains only RTX 4090/5090 task counts and class-specific generation confirmations; it no longer renders selected-task prompt details. Local-only `confirm_group`, `cancel_group`, and `retry_failed_group` mutations use the existing task-store lock, never start a GPU order, and never remove completed artifacts. The prompt workspace uses the original two-click 256-pixel resolution drawing grid; unavailable RTX 5090-only selections explain the executor blocker without starting a rental.
- Completed images live only in the local image library (`AI_IMAGE_LIBRARY_ROOT`, default `D:\AI-Video-Library\images`) under a dated task directory. The UI uses loopback-only `/api/local-images/<task_id>/output` and `/thumbnail` routes, which resolve only verified task-relative artifacts.
- The local image routes return explicit MIME type, exact `Content-Length`, private no-transform caching, and `nosniff` headers from already-read verified bytes. UI verification validates the actual response body and decoded image dimensions; `Content-Length` is an optional consistency check. Published artifacts verify both the exact PNG and a non-empty WebP thumbnail no larger than 512 px before serving.
- `docs/IMAGE_E2E_GOLDEN_BASELINE.json` is the compact immutable acceptance record for the first real image E2E; it contains only pinned runtime/model hashes and sanitized artifact evidence. `image:session:plan` is a read-only local planner for future RTX 4090 image batches (maximum eight tasks), and `image:session:simulate` exercises its one-order, one-model-stage, sequential-task semantics through fake dependencies only. Neither command calls a provider or mutates a task.
- The restricted Agent assigns a UUID `stage_run_id` before returning every accepted stage POST. All stage polling correlates that ID, so a later inference cannot accept an earlier same-name terminal record. `image:session:seed-e2e` is an idempotent local-only two-task seed, while `image:session:execute` remains dry-run unless `--execute`, exact task IDs, immutable hashes, live provider revalidation, the USD 1.50 creation-fee-inclusive cost cap, and the USD 1.00 wallet reserve all pass. Session and per-task receipts are fsync-plus-atomic and exclude prompts, tokens, signed URLs, and complete endpoints.
- Long paid image sessions must start through `image:session:supervisor:start`, which detaches the only worker allowed to call `runLiveImageSession`. The supervisor status and wait commands read local sanitized state only; they never call the provider. A prior session receipt is rotated only after terminal cancellation, zero active-order reconciliation, and exact untouched target-task checks.
- Image-session worker state is terminalized locally for normal completion, uncaught exceptions, unhandled rejections, and dead `starting`/`running` PIDs. Accepted or submitting inference evidence remains `ambiguous` and cannot be retried automatically. A locally finalized task can be recovered only when its existing PNG and thumbnail verify byte-for-byte; recovery preserves its result and attempt history. Session cleanup receipts retain two-zero-order confirmation and watchdog-disarm evidence.
- `scripts/clore/run-image-e2e.ts` uses this local claim/finalize contract. Its pre-rental model check resolves five immutable sources with only local Civitai/Hugging Face credentials, validates advertised sizes against the pinned SHA-256 manifest, and passes only temporary signed download URLs to the Agent. It must not claim a task until the remote runtime and all five model files have succeeded; no Supabase image queue, Storage path, or cloud credential is part of this image E2E path.
- Model-source preflight uses bounded headers-only **GET** requests (never HEAD), with the fixed preflight user agent and immediate response-body disposal. Civitai bearer authentication is used only for its local initial redirect request; redirected hosts never receive it. Each outbound Agent URL has passed a real GET status/size check, while receipts retain only model identity, size, status, final hostname, redirect count, and `validatedMethod: GET`.
- The restricted Agent sends its fixed model-fetch `User-Agent` and octet-stream `Accept` headers for both fresh and Range-resume downloads. A model HTTP 401/403 is recorded as sanitized structured `model_download_http_error` evidence. Before task claim or inference, the coordinator may regenerate all five temporary URLs and POST the same manifest once more on the same order; a second 401/403 fails closed as `model_download_authorization_failed_after_refresh` and never starts inference or a replacement order.
- Model downloads use one bounded, sequential `.part` resume loop (four transport attempts, fixed Range and identity-encoding headers). It validates response length and Content-Range before appending, retains partial bytes across transient EOF/socket interruptions, throttles progress state writes, and emits sanitized structured incomplete/range/oversize/SHA evidence. A canceled pre-claim `model_download_incomplete_after_retries` may regenerate the exact five temporary URLs and POST `/stage/models` once more on the same order; verified files are retained and no inference POST is permitted until all five verify.
- The Controller keeps `request_upstream()` bytes-only. Every JSON upstream request goes through `request_upstream_json()`, which produces compact UTF-8 JSON and the JSON content type before calling that transport. A non-2xx ComfyUI `/prompt` result retains a sanitized structured HTTP status, upstream error, node errors, and prompt-validation information without retaining prompt text, signed URLs, or credentials.
- The model resolver retains local identities and source metadata, but the only outbound manifest is `toAgentModelManifest()`: an explicit five-field projection (`role`, `filename`, temporary `url`, `sha256`, `size_bytes`) for exactly five approved roles. The same projection is exercised before rental and used for the Agent request, so local IDs, source/provider fields, credentials, and paths cannot leak across the remote boundary.
- The fresh-run receipt is fsync-plus-atomic. It is persisted as `inference_submitting` before the sole inference POST, as `inference_accepted` after HTTP 202 and before any status GET, and records only sanitized terminal artifact metadata. The Agent saves the Controller job/prompt identifiers and requested dimensions as soon as the Controller returns HTTP 202; a dimension failure also records only sanitized job/prompt identifiers, requested/actual dimensions, and PNG size/hash. An incomplete task with a prior `submitting`, `accepted`, or `succeeded` receipt is fail-closed and requires manual recovery before any later provider mutation. The same receipt records verified artifact download, local publication, exact task finalization, UI verification, and confirmed exact-order cancellation.
- Agent health, status, inference-poll, and artifact-metadata GETs use one bounded authenticated transport wrapper: each request has a 15-second abort timeout, records only route-level sanitized diagnostics, and treats temporary proxy/socket failures as GET-only retries. A stage POST or inference POST is never replayed. Continuous status loss is tolerated for up to eight minutes with an Agent-health probe, then reconciles the exact persisted order and records a structured `agent_transport_outage_exceeded` result before normal cleanup.
- Agent GET success is route-aware: a HTTP 200 response is accepted only after bounded body parsing and the canonical `/healthz`, `/status`, or artifact-metadata schema validates. Empty, HTML, invalid-JSON, oversized, or wrong-schema HTTP 200 proxy responses are sanitized as `agent_proxy_non_agent_response` diagnostics and use the existing GET-only outage path; they never replay a stage or inference POST. Agent status and health requests send no-cache headers and an attempt-only cache-busting query without recording the endpoint or Authorization value.
- A previous receipt may be rotated only when it proves a canceled pre-inference failure, the exact task is still `waiting_for_gpu`, and a fresh centralized provider read reports zero active orders. The prior sanitized receipt is retained under ignored diagnostics; it is never deleted or overwritten.
- One narrow exception permits only task `eefc2b5b-5f25-4d82-aeeb-3b8ff501a1a0` to return from `failed` to `waiting_for_gpu`: the prior receipt must prove the canceled, artifact-free exact `result_dimensions_mismatch:384x384` failure after its one inference POST, with a retryable local task and zero active provider orders. If structured failure data exists it must also prove requested `768x768` and actual `384x384`. The prior receipt is archived before a new run ID is created; any ambiguous or artifact-bearing inference remains fail-closed.
- A failed pre-order receipt with no order ID or endpoint is also safe to rotate when it proves no inference/artifact/finalization mutation and the shared fresh active-order snapshot is zero. The same snapshot is reused for the first create attempt when younger than ten seconds. A create-order 429 is reconciled, waits its sanitized `Retry-After` or a 90-second fallback plus local jitter, and retries the identical payload at most once; it never changes host or creates in parallel.
